# Repository Overview
The repository is an Amplication-generated monorepo that contains two npm applications under `apps/`:

- `hotel-management-service-server`: a NestJS 10 API that exposes both REST (Swagger) and GraphQL endpoints backed by a PostgreSQL database via Prisma.
- `hotel-management-service-admin`: a React 18 / React-Admin 5 console bundled with Vite that consumes the server’s GraphQL API through an Apollo client.

Both applications ship with Dockerfiles, environment templates, and independent package manifests, enabling separate builds and deployments while sharing a common domain language (hotel, room, reservation, customer).

# High Level Architecture
The backend application (`src/` in the server project) wires domain-specific NestJS modules into `AppModule`. Controllers and GraphQL resolvers delegate to thin services that extend Amplication-generated base classes and rely on `PrismaService` for persistence. The API is bootstrapped in `main.ts`, where global pipes, exception filters, Swagger/OpenAPI, and a placeholder microservice connector are registered. Static assets (Swagger UI) are served through `ServeStaticModule` configured by `ServeStaticOptionsService`.

The admin UI is a React-Admin shell (`App.tsx`) composed of `Resource` definitions mapped to generated CRUD view components. Data access flows through `data-provider/graphqlDataProvider.ts`, which wraps an Apollo client (`@apollo/client`) configured against `VITE_REACT_APP_SERVER_URL`. Authentication helpers under `auth-provider/` manage bearer/basic tokens in `localStorage` and expect a `login` GraphQL mutation.

# Major Modules or Bounded Contexts
- **Backend domain modules**: `hotel`, `room`, `reservation`, `customer`—each with base DTOs, REST controllers, GraphQL resolvers, and Prisma-backed services.
- **Platform modules**: `prisma` (database access), `health` (readiness checks), `providers/secrets` (ConfigService-backed secret lookup), `decorators`, `validators`, `filters`, and `swagger` assets.
- **Frontend domain bundles**: per-entity React-Admin screens under `hotel/`, `room/`, `reservation/`, `customer/`, paired with generated GraphQL types in `src/api/`.
- **Frontend infrastructure**: `data-provider/`, `auth-provider/`, shared `Components/` (pagination), theming, and login page assets.

# High level responsibilities of each module
## Backend
- `AppModule` (`src/app.module.ts`): composes all Nest modules, configures global `ConfigModule`, `ServeStaticModule`, and Apollo GraphQL driver.
- Domain modules (`hotel`, `room`, `reservation`, `customer`): expose REST endpoints (e.g., `hotel.controller.ts`) and GraphQL resolvers (e.g., `hotel.resolver.ts`) that forward to services extending base CRUD logic in `base/` directories. Relation helpers (e.g., `HotelServiceBase.findRooms`) encapsulate Prisma traversals.
- `PrismaModule`/`PrismaService`: wraps the generated Prisma client (`prisma/schema.prisma` models Hotel/Room/Reservation/Customer) and manages connection lifecycle.
- `HealthModule`: provides `/api/_health/live` and `/api/_health/ready` endpoints, with readiness dependent on `prisma.$queryRaw`.
- `providers/secrets`: simple secret abstraction reading env values via `ConfigService` (no external secrets manager integration beyond the stub).
- Shared utilities: custom Swagger query decorator (`decorators/api-nested-query.decorator.ts`), `ValidationPipe` usage, Prisma error helpers (`prisma.util.ts`), JSON validator (`validators/is-json-value-validator.ts`), and Swagger configuration (`swagger.ts`).

## Frontend
- `App.tsx`: registers React-Admin resources and ties in theming, dashboard, and login page.
- `auth-provider/ra-auth-jwt.ts` and `ra-auth-http.ts`: handle authentication flows, storing bearer/basic tokens in `localStorage` and surfacing identities to React-Admin.
- `data-provider/graphqlDataProvider.ts`: instantiates the Apollo client with auth link and delegates CRUD operations to `ra-data-graphql-amplication`.
- Resource directories (`hotel/`, `room/`, etc.): supply list/show/create/edit components built from React-Admin primitives, relying on generated GraphQL argument/type helpers in `src/api/`.
- Shared UI (`Components/Pagination.tsx`, `pages/Dashboard.tsx`, `Login.tsx`): provide navigation, onboarding, and custom pagination behaviour.

# Internal dependencies
- REST controllers and GraphQL resolvers depend on their corresponding services, which all consume `PrismaService`; each module is imported into `AppModule` and exported for reuse.
- Relation endpoints (e.g., `/customers/:id/reservations`) and GraphQL resolve fields share the same service methods, aligning REST and GraphQL behaviour.
- Global concerns (`ValidationPipe`, `HttpExceptionFilter`) are applied in `main.ts`, affecting every controller.
- The admin UI relies on the GraphQL schema generated by the server—resource components import matching TypeScript definitions from `src/api/` that mirror the Prisma models.
- Authentication expectations span both apps: the UI invokes a `login` mutation while Swagger advertises JWT bearer auth, but the server currently lacks an auth module, creating a dependency gap between client expectations and API capabilities.

# External dependencies (APIs, DBs, queues, SDKs, cloud services)
- **Database**: PostgreSQL accessed through Prisma Client (`@prisma/client`, migrations under `prisma/`).
- **GraphQL runtime**: `@nestjs/graphql` with the Apollo server driver; frontend uses `@apollo/client`.
- **REST tooling**: `@nestjs/swagger` for OpenAPI and Swagger UI assets served statically.
- **Frontend frameworks**: React 18, React-Admin 5 (which pulls in MUI), Vite build tooling, `ra-data-graphql-amplication` for CRUD adapters.
- **Containerization**: Multi-stage Dockerfiles (Node 18 for server build/runtime, nginx 1.22 for UI) enable deployment without additional orchestration services.

# Cross cutting concerns (auth, logging, messaging, caching, events)
- **Authentication & Authorization**: Swagger is configured with bearer auth and `Public` decorators exist, but there is no implemented guard, login resolver, or JWT issuance—authentication is effectively missing despite client expectations.
- **Validation**: Global `ValidationPipe` transforms and validates DTOs; class-validator decorators appear in generated inputs.
- **Error handling**: `HttpExceptionFilter` converts Prisma known errors (P2000/P2002/P2025) into HTTP responses and strips security metadata when marked public.
- **Documentation**: Swagger document is generated at bootstrap with custom security adjustments; GraphQL auto-generates schema files (`autoSchemaFile`).
- **Static assets**: `ServeStaticOptionsService` logs configuration and serves Swagger UI and optionally external static roots.
- **Observability and messaging**: No logging strategy beyond Nest defaults, no metrics, messaging, caching, or event bus integrations are present.

# Complexity indicators and risks
- **Generated base layers**: Core CRUD logic lives in Amplication-generated `base/` files; regenerating could overwrite customisations, so extensions must stay in non-base wrappers.
- **Authentication gap**: Client code depends on a `login` mutation and bearer tokens, but the server lacks any auth controllers, guards, or JWT issuing logic—deployment will require implementing or stubbing these endpoints.
- **Database seed scripts**: `scripts/customSeed.ts` and `seed.ts` instantiate Prisma but do not populate data, signalling unfinished setup routines.
- **Microservice placeholder**: `connectMicroservices.ts` is empty, so enabling microservices will need additional configuration.
- **Testing coverage**: Only `health.service.spec.ts` exists; critical domain flows and auth are untested.
- **Operational configuration**: Secrets manager service merely surfaces environment variables; there is no integration with external secret stores or rotation, which may be inadequate for production.
